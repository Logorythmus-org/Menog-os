# Phase 24B — Local Cryptographic Identity & Signed Envelopes

**Gate:** 24B · **Date:** 2026-10-01 · **Mode:** NO NETWORK · **Status:** implemented + proven

## 1. Primitive and version

| Item | Pinned value |
|:--|:--|
| Algorithm | `ed25519-deterministic-v1` — Ed25519 (EdDSA, RFC 8032) via `node:crypto` (platform-supported; engines ≥ 22). Deterministic signatures: no nonce, no padding, no ECDSA-k pitfalls. |
| Crypto schema | `menog-federation-crypto/v0` |
| Fingerprint | `fp-sha256-<64 hex>` over the RAW 32-byte Ed25519 public key (prefix defined once in 24A as `NODE_FINGERPRINT_PREFIX`; 24B re-exports it — the two gates cannot drift) |
| NodeId | `node-<same 64 hex>` — the 24A canonical injective derivation; a NodeId IS its fingerprint |

No CA, WebPKI, DID, blockchain, wallet, certificate chain, or trust anchor exists in this
module and none is claimed anywhere.

## 2. Canonical encoding

The signed bytes are **SHA-256 over the frozen 22A canonical JSON**
(`canonicalDurableJson`: recursively sorted keys, no insignificant whitespace,
`undefined`-free) of the subject body. Consequences, all test-pinned:

- key order and insignificant formatting never change a signature;
- any field-value change breaks every signature over the subject;
- signatures are deterministic: signing the same subject twice yields identical bytes.

Both 24A subjects are signed by the same functions: identity documents
(`signIdentityDocument`) and federation messages (`signFederationMessage`). The verifier
port accepts either (schema-agnostic subject hashing).

## 3. The signer/verifier relationship to 24A

`generateLocalSigningIdentity()` produces the in-memory identity;
`makeIdentitySignatureVerifier(publicKeyHex)` produces the exact object 24A's
`IdentitySignatureVerifier` port consumes. The verifier answers TWO questions and nothing
else:

1. was this subject signed by the private key of this public key (Ed25519 verify over the
   canonical digest);
2. does the subject's OWN fingerprint claim (`fingerprint` / `senderFingerprint`) equal
   this key's fingerprint — **checked BEFORE the signature**, so a subject claiming
   identity Y while signed by key X is refused (`fingerprint_claim_mismatch`) regardless
   of cryptographic validity.

A verification result is AUTHENTICATION data. It is consumed only by the 24A trust
decisions, every one of which carries `authority: "none"`. **Verification never
authorizes.**

## 4. Private-key handling

- Generated by the platform (`generateKeyPairSync("ed25519")`), held in a module-private
  `WeakMap` keyed by the frozen public identity object.
- There is NO export path, NO serialization path, NO accessor, NO PEM/DER emission of the
  private key anywhere in the public API (test-pinned: the identity object's own
  enumerable surface is exactly `algorithm, fingerprint, nodeId, publicKeyHex`).
- The PUBLIC key hex and fingerprint are safe to persist and to re-derive from each other.

## 5. Secret-at-rest limitations (exact; no overclaim)

1. **Process-memory only.** The private key exists solely in the live process. A restart
   loses the key pair irrecoverably. No key file, keyring, keystore, or persistence path
   exists in v0 (test-pinned: no `writeFile`/`appendFile`/`createWriteStream`/
   `DatabaseSync` in module code).
2. **Restart identity = PUBLIC-facts continuity.** `verifyRestartIdentity` proves only
   that persisted public facts re-derive (public key → fingerprint → NodeId) and refuse
   when inconsistent. Private continuity across restarts is NOT provided and NOT claimed.
3. **No memory protection.** Nothing encrypts memory; no mlock, TPM, secure enclave, or
   OS-keychain integration exists. A hostile party with a memory dump, swap image, or
   debugger can extract the private key. Host compromise is out of scope.
4. **Leak prevention is defense-in-depth, not a guarantee.** `FEDERATION_SECRET_KEY_DENYLIST`
   (same normalized-key discipline as the 22C raw-output denylist) plus
   `findSecretKeyPaths`/`payloadContainsSecretKeyMaterial` deny any structured payload
   carrying private-key-shaped keys at any depth; `looksLikeEncodedPrivateKey` is a
   best-effort base64/PKCS#8 tripwire for free-text surfaces. Shapes are scanned, not
   semantics; clever encodings are not provably excluded.

## 6. Rotation / revocation — actually-proven semantics ONLY

- **Proven:** `rotateLocalIdentity` — a fresh key pair canonically yields a fresh
  fingerprint and fresh NodeId. Key replacement is RE-IDENTITY, never in-place mutation.
  The previous NodeId is returned so the caller retires it through the 24C peer trust
  machine (quarantined → retired; no resurrection path). Test-pinned both ways: the fresh
  identity's verifier accepts fresh-key signatures; the old key's verifier refuses them
  (`fingerprint_claim_mismatch`).
- **Not provided, not claimed:** revocation lists, expiry metadata, threshold/rotation
  ceremonies, cross-node key agreement, escrow.

## 7. Failure modes (fail closed)

`malformed_input` · `fingerprint_claim_mismatch` · `signature_malformed` (not 64 decoded
bytes) · `unsupported_algorithm_shape` · `signature_invalid`. Any tamper — field flip,
extra field, protocol change, whitespace-sensitive byte change — invalidates the
signature because the canonical digest is total over the subject body.
